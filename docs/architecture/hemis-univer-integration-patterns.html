🔄 HEMIS ↔ Univer Ma'lumot Almashish

Markaziy vazirlik server (HEMIS-back) va 224 ta OTM Univer (Yii2 PHP) o'rtasida ma'lumot almashishning 8 ta strategiyasi. Har birining afzalligi, kamchiligi va HEMIS uchun mosligi.

📅 2026-05-13 🏛️ 1 markaziy server 🏫 224 OTM Univer 📊 25K+ event/day

1. Tizimlar konteksti — kim kim bilan gaplashadi?

Ma'lumot 2 yo'nalishda harakat qiladi. Inbound — Univer markazga yuboradi (talaba, o'qituvchi, nashr). Outbound — markaz Univer'ga yuboradi (klassifikator, qoidalar, hisobotlar).

2. Ma'lumot almashishning 8 ta strategiyasi

🔁 Synchronous REST
Hozir
Univer ──HTTP POST──▶ HEMIS
Univer ◀──200 OK + JSON── HEMIS
# Bloklayotgan, har request o'z javobini kutadi
✓ Afzalligi
  • Univer (PHP) uchun standart — har dasturchi biladi
  • Hozir 175/175 contract test ishlaydi
  • Debug oson — HTTP log, Postman
  • Yangi infrastruktura kerak emas
✗ Kamchiligi
  • Bloklayotgan — HEMIS sekin bo'lsa Univer kutadi
  • Peak time 50 OTM bir vaqtda → connection pool tugaydi
  • Back-channel yo'q — markaz Univer'ga push qila olmaydi
  • Replay yo'q — request yo'qolsa, qayta yuborish manual
VERDICT: Inbound (Univer → markaz) uchun saqlanadi.
🪝 Webhook (Callback)
Outbound
HEMIS ──POST callback──▶ Univer
HEMIS ◀──200 OK── Univer
# Markaz event sodir bo'lsa Univer'ga POST qiladi
✓ Afzalligi
  • Markaz → Univer push imkoniyati (klassifikator update)
  • Univer PHP'da oddiy controller (kerakli)
  • Real-time delivery (1-2 sekund)
✗ Kamchiligi
  • Univer endpoint public bo'lishi kerak (auth + IP whitelist)
  • Univer o'lsa → callback yo'qoladi (retry mexanizm kerak)
  • 224 endpoint URL boshqarish (URL change → markazda yangilash)
  • Network glitch → duplicate delivery (idempotency kerak)
VERDICT: Outbound delivery uchun OK, lekin retry/DLQ kerak.
⏰ Polling (Pull)
Oddiy
Univer cron ──GET /updates?since=T──▶ HEMIS
Univer cron ◀──[events…]── HEMIS
# Univer har N daqiqa markazdan tortib oladi
✓ Afzalligi
  • Univer'da public endpoint kerak emas (firewall ichida)
  • Reliability — yo'qotish yo'q (Univer o'lsa, keyingi pull olib keladi)
  • Implement oddiy — cron + REST
✗ Kamchiligi
  • Latency yuqori — poll interval (5-15 min)
  • Markazga 224 × N pull/min yuk (bo'sh javob ham resurs oladi)
  • Markazda since cursor saqlash kerak
  • Real-time emas — qoida lock 15 min kech kelishi mumkin
VERDICT: Past prioritet ma'lumotlar uchun (klassifikator).
📡 WebSocket / SSE
Murakkab
Univer ──ws://...── HEMIS [persistent]
HEMIS ──push event──▶ Univer
# Doimiy connection, real-time bidirectional
✓ Afzalligi
  • Real-time (millisekund latency)
  • Bidirectional — har ikki tomon push
✗ Kamchiligi
  • 224 ta persistent connection — markazda yuk
  • Univer PHP — WebSocket server zaif (Ratchet, Swoole — Yii2 standart emas)
  • Network nestabil → reconnect logic murakkab
  • Load balancer sticky session
  • Real-time ko'pchilik HEMIS use-case'ga ortiqcha
VERDICT: HEMIS use-case'ga mos kelmaydi.
⚡ gRPC Streaming
PHP zaif
Univer ──HTTP/2 stream── HEMIS
# Bidirectional streaming, Protobuf
✓ Afzalligi
  • Tezroq JSON'dan (binary Protobuf)
  • Strong typing (.proto schema)
  • Bidirectional streaming
✗ Kamchiligi
  • PHP gRPC ekstension — install murakkab, hosting cheklangan
  • Yii2'da rasmiy support yo'q (community)
  • Debug qiyin — HTTP'dan farqli, log standart emas
  • 224 OTM dasturchilarini qayta o'rgatish kerak
  • JSON over HTTP — 99% use case yetarli
VERDICT: PHP ekosistema mos kelmaydi.
🐰 RabbitMQ (AMQP)
Alternativ
Univer ──publish──▶ RabbitMQ ◀──subscribe── HEMIS
# Broker queue — async, persistent
✓ Afzalligi
  • PHP'da yetuk client (`php-amqplib`, Yii2 ext)
  • Asinxron — Univer fire-and-forget
  • Retry + DLQ built-in
  • Routing flexibility (exchange types)
✗ Kamchiligi
  • Replay cheklangan — bir o'qildi → o'chadi (ack model)
  • Throughput Kafka'dan past (10-50K msg/s vs Kafka 1M+)
  • Multi-consumer murakkab (fanout exchange)
  • Geo-replication zaif (federation plugin)
VERDICT: Kafka'ga alternativ — kichik volume uchun OK.
📨 Kafka (to'g'ridan)
PHP cheklov
Univer (PHP) ──rdkafka──▶ Kafka topic ◀── HEMIS (Spring)
# Univer to'g'ridan Kafka'ga producer/consumer
✓ Afzalligi
  • 1M+ msg/s throughput
  • Replay, retention, partitioning
  • Multi-consumer (analytics, audit, notification)
✗ Kamchiligi
  • PHP rdkafka — C extension install qiyin shared hosting'da
  • 224 ta Univer Kafka credential boshqarish
  • Univer dasturchilari Kafka client kodga moslashishi
  • Network — har OTM markaz Kafka'ga TCP 9092 ochishi kerak
  • Davlat tarmoq policy'lari odatda HTTPS only
VERDICT: Univer-side cheklov, real bo'lmagan.
⭐ Hybrid: REST + Internal Kafka
Tavsiya
Univer ──HTTP POST──▶ HEMIS ──outbox──▶ Kafka
Kafka ──▶ Consumer 1 (DB), Consumer 2 (Univer push), Consumer 3 (analytics)
# Univer ↔ markaz = REST. Markaz ichida = Kafka.
✓ Afzalligi
  • Univer kod o'zgarmaydi (REST davom etadi)
  • Markaz ichida event-driven (multi-consumer, replay)
  • Outbound push — Kafka consumer Univer'ga REST callback yuboradi
  • Decoupling: yangi consumer qo'shish Univer'ga ta'sir qilmaydi
  • Davlat firewall talabiga mos (faqat HTTPS Univer ↔ markaz)
✗ Kamchiligi
  • Markaz ichida 2 ta texnologiya boshqarish (REST + Kafka)
  • Outbox pattern — DB poller latency (~1s)
  • K8s + Strimzi expertise kerak (production)
VERDICT: Eng yaxshi tanlov — Univer kontrakti saqlanadi, markaz scaling beradi.

4. Kafka chuqur tahlil — nima foyda va kamchilik?

Yuqorida ko'rdik: Kafka to'g'ridan Univer bilan mos kelmaydi (PHP cheklov). Lekin markaz ichida ishlatsa katta foydalar beradi. Quyida konkret afzalliklari va xavflari — HEMIS use-case'da.

🔓 Decoupling (Univer'lar bir-biriga ta'sir qilmaydi)

1 OTM "sekin" bo'lsa, qolgan 223 ta yuk olmaydi. Har consumer alohida tempda ishlaydi.

Univer #337 sekin → Kafka topic'ga yozildi → Consumer #337 ish boshqarib, qolganlar normal davom etadi.

⏪ Replay — event'larni qayta o'qish

Bug topilsa, 3 oy oldingi event'larni qayta consume qilib jadval'ni qayta quryapsiz.

Talaba GPA hisoblash bug → fix → consumer group reset → 100K event qayta hisoblanadi.

👥 Multi-consumer (bir event → ko'p ish)

Bitta employee event'ga bir nechta tinglovchi: DB yozish, audit log, notification, analytics.

EmployeeAdded → Consumer 1: write DB, Consumer 2: SMS HR'ga, Consumer 3: BIMM sync, Consumer 4: stats.

💾 Persistence (event source of truth)

Event'lar 30+ kun saqlanadi. Yangi consumer qo'shilsa, eski event'larni ham o'qiy oladi.

Yangi analytics service ish boshlasa, 30 kunlik tarix'ni o'qib trendlarni quryapdi.

🌊 Backpressure absorbsiya

Consumer sekinroq bo'lsa, queue ortadi (yo'qotmasdan). Consumer tezlasa, catch up qiladi.

Semestr boshi 50K event/min → Kafka buffer'da saqlandi → Consumer 1 soat ichida hammasi ish boshqaradi.

📊 Order kafolat (per partition)

Bir OTM event'lari aynan tartibda qayta ishlanadi (key = university_code).

Talaba: ADD → UPDATE → DELETE. Univer #401 uchun bu tartib hech qachon buzilmaydi.

🌍 Geo-replication (DR)

Mirror Maker 2 — Toshkent → Samarqand DC. Primary o'lsa, DR cluster qayta ishga tushadi.

Toshkent DC yong'in → DNS switch 30 min → Samarqand DC ish boshqaradi (RPO <5 min).

🔄 Outbox pattern — transactional safety

DB write + Kafka publish bir transaction'da. Crash bo'lsa ham event yo'qolmaydi.

INSERT student + INSERT outbox_event = atomic. Poller keyin Kafka'ga jo'natadi (at-least-once).

🔧 Operatsion murakkablik

3-broker cluster, ZooKeeper/KRaft, JVM tuning, partition rebalance, disk monitoring.

SRE jamoa kerak — har broker upgrade, disk ko'paytirish, broker o'limini qayta ishlash.

📜 Schema evolution

Producer schema o'zgartirsa, eski consumer break bo'lishi mumkin. Schema Registry kerak.

Yangi field qo'shildi → eski consumer Avro deserialize xato → BACKWARD compatible bo'lishi kerak.

⏱️ Eventual consistency

Outbox poller + Kafka publish — sub-second emas. Real-time muhim bo'lsa, REST.

Student qo'shildi → 1-3 sekund keyin Kafka'da → 1-3 sekund keyin consumer ishladi. Total: 2-6s.

🐘 Yangi tech — learning curve

Jamoa Spring + JPA biladi, Kafka esa yangi. 1-2 oy o'rganish vaqti.

Producer config, consumer group, offset commit, idempotent producer, exactly-once — har birini o'rganish kerak.

🔁 Idempotency consumer'da

At-least-once delivery → consumer duplicate event'larni hal qilishi kerak.

EmployeeAdded 2 marta keldi → consumer event_id tekshirib, ikkinchi marta skip qilishi kerak.

💸 Infrastruktura xarajati

3-broker × 16GB RAM × SSD 500GB + monitoring stack — bo'sh emas.

VM xarajati ~$200-500/oy (on-premise yoki cloud). Kichik volume uchun overkill.

🐛 Debugging qiyin

Event distributed — qaysi consumer xato qildi, qaysi offset, qaysi partition?

Talaba sync ishlamadi → log Kafka, consumer, DB'da alohida → trace ID + Sentry kerak.

🚧 Univer side'da ishlatib bo'lmaydi

Asosiy use-case (Univer ↔ markaz) uchun Kafka direct emas — PHP cheklov.

Univer hali ham REST orqali yozadi. Kafka faqat markaz ichki = qiymat cheklangan, lekin real.

📈 Volume yuqori

Mingdan ortiq event/sec, peak time burst. HEMIS: 25K/day peak ~50/sec — chegarada.

🔀 Multi-consumer

Bir event uchun 3+ tinglovchi. HEMIS: DB + Univer push + analytics + audit. Ha, kerak.

⏪ Tarix saqlash

Event'lar 30+ kun saqlanishi, replay imkoniyati. HEMIS: audit/compliance uchun foydali.

🌊 Asinxron kerakli

Producer kutmaydigan natija. HEMIS: outbound push (markaz → Univer) async OK.

📉 Volume past

<100 event/sec — Kafka overkill. RabbitMQ yoki to'g'ridan DB INSERT yetadi.

🎯 Single consumer

Faqat 1 tinglovchi — Kafka mantig'i ortiqcha. Database queue (table) yoki Redis Streams yetadi.

⚡ Strict real-time (<100ms)

Trading, gaming. HEMIS: 1-5s ham OK, demak Kafka mos.

🤝 Synchronous request-response

Klient javob kutadi (API call). Kafka — pub/sub fire-and-forget. REST kerak.
