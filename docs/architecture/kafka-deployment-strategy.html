2. 7 ta deploy varianti

🐳 Docker Compose
Hozir
Single broker, KRaft mode, hozir docker-compose.yml'da mavjud (Stage 0).
  • Tezkor sinov — 1 buyruq bilan ishga tushadi
  • Loyihada allaqachon konfigurirovangan
  • KRaft mode — ZooKeeper kerak emas
  • Single Point of Failure (SPOF)
  • Replication factor=1 → broker o'lsa data yo'qoladi
  • Production'ga mutlaqo nomos
VERDICT: Faqat Dev/Stage — production'da har doim distributed cluster.
🖥️ Bare-metal / VM
Klassik
3 ta alohida VM/server (har biri 8-16GB RAM, SSD 500GB), manual deploy.
  • To'liq nazorat — data residency 100%
  • Cloud/vendor lock-in yo'q
  • Litsenziya pul yo'q
  • Manual upgrade, monitoring, backup
  • Sysadmin jamoa 24/7 kerak
  • Disk full, GC pause — manual hal qilish
  • Version migration — kechalik downtime
VERDICT: OK agar K8s yo'q va ops jamoa Java/Kafka kuchli biladi.
⚡ Strimzi (K8s Operator)
⭐ Tavsiya
CNCF rasmiy Kafka operator. Declarative YAML — kubectl apply bilan cluster.
  • Open source (Apache 2.0) — bepul
  • Auto rolling upgrade, self-healing pod
  • Mirror Maker 2 — DR cluster (geo-replication)
  • Kafka Connect, Cruise Control, User Operator
  • Loyihada helm/ papka — K8s deploy tayyor
  • K8s expertise kerak (operator, CRD, helm)
  • StatefulSet + PV management — disk full xavf
  • Strimzi 0.x → 0.y upgrade — CRD breaking changes
VERDICT: Eng yaxshi tanlov — K8s + open source + production-ready.
💼 Confluent Platform
$$$$
Self-managed enterprise — Schema Registry, ksqlDB, Control Center, RBAC.
  • Enterprise feature (RBAC, audit log, tiered storage)
  • 100+ rasmiy connector
  • 24/7 vendor support
  • Litsenziya pul — vazirlik budget mos kelmasligi mumkin
  • Vendor lock-in (ksqlDB, Control Center)
  • Strimzi bilan deyarli har feature mavjud (bepul)
VERDICT: Davlat sektorida xarajat asoslab bo'lmaydi.
☁️ Managed Cloud
⚠️ Data
Confluent Cloud, AWS MSK, Aiven, Azure Event Hubs — zero ops.
  • Zero ops — provider hamma narsani boshqaradi
  • Auto scaling, SLA 99.95%+
  • Tezkor PoC (5 daqiqa)
  • Data sovereignty — davlat ma'lumotlari cloud'da
  • Internet bog'liqlik (vazirlik network → cloud)
  • Egress fee (ma'lumot transferi pul)
  • Latency 50-100ms (vs local 1ms)
VERDICT: Davlat IT politikalari rad etishi yuqori ehtimol.
🦀 Redpanda
Innovatsion
Kafka-compatible alternative — Rust, ZooKeeper/JVM yo'q. 10× kam resurs.
  • 10× kam resurs (JVM yo'q)
  • 6× kam latency (Rust + single binary)
  • Operatsion soddaroq (1 binary)
  • K8s operator bor
  • Kafka emas — edge case'larda farq qilishi mumkin
  • Community kichik (Apache Kafka 1000× ko'p)
  • Enterprise tier pulli (Redpanda BSL)
  • Davlat IT konservativ — "Apache Kafka" tanish brend
VERDICT: Texnik zo'r, lekin brend xavfi bor.
🌀 Apache Pulsar
ADR zid
Geo-replication, multi-tenancy native. Kafka emas — boshqa API.
  • Geo-replication built-in
  • Multi-tenancy native (per-OTM uchun ideal)
  • Tiered storage out-of-box
  • Kafka emas — ADR-0007 Kafka tanlangan
  • Spring spring-kafka ishlamaydi
  • Code'ni Pulsar client'iga moslash kerak
  • Alohida ADR talab qiladi (qayta qaror)
VERDICT: ADR-0007 bilan zid — yangi qaror talab qiladi.

4. Bosqichli joriy qilish — Stage 0 → 4

0
Stage 0 — Infrastructure Ready
✅ Bajarilgan (2026-05-06)
  • docker-compose.yml'da apache/kafka:3.7.0 KRaft single broker
  • Volume kafka-data (host disk persistence)
  • Auto-create topics off (manual control)
  • Network hemis-network ichida
1
Stage 1 — Outbox Pattern (KEYINGI)
⏳ 1-2 sprint kutilmoqda
  • outbox_event jadvali (V015 changeset)
  • spring-kafka dependency (service modul)
  • OutboxPublisher + OutboxEvent entity
  • Scheduled poller (1s interval) — outbox → Kafka topic
  • Local dev'da test — Univer sync → outbox → consumer
2
Stage 2 — Staging Multi-broker
⏳ 2-3 sprint
  • 3-broker docker-compose (replication factor=3)
  • Schema Registry — Karapace (open source alternative Confluent SR)
  • Avro schema definition (Employee, Classifier, Rule events)
  • Monitoring — kafka-exporter + Grafana dashboard
  • Kafka UI (web admin) — topic/consumer group ko'rish
3
Stage 3 — Production K8s + Strimzi ⭐
⏳ 4-6 sprint
  • K8s + Strimzi 0.4x.x operator (helm chart)
  • 3-broker KRaft cluster (anti-affinity, alohida node'lar)
  • min.insync.replicas=2, replication.factor=3
  • TLS + SASL/SCRAM-SHA-256 auth (per-app credentials)
  • Network policy — faqat hemis-back namespace'dan
  • Persistent volume — SSD storage class
4
Stage 4 — Advanced (DR + Observability)
⏳ Production'dan keyin
  • Mirror Maker 2 — primary → DR cluster (RPO < 5 min)
  • DR cluster alohida data center (Toshkent → Samarqand)
  • Cruise Control — partition rebalance, broker workload optimize
  • Kafka Connect — Debezium PostgreSQL CDC (outbox bypass — to'g'ridan-to'g'ri DB → Kafka)
  • Tiered storage — eski event'lar S3/MinIO'ga (cheap, infinite retention)
  • Schema evolution policy — BACKWARD compatibility majburiy

6. Risklar va mitigatsiya

K8s expertise yo'qligi YUQORI

Strimzi operator deploy/maintain qilish K8s/CRD bilim talab qiladi. Loyihada DevOps jamoa hozircha cluster boshqarmagan.

Mitigatsiya: Stage 2 (3-broker docker-compose) bilan boshlash, K8s migration Stage 3'da. DevOps trening + Strimzi rasmiy hujjat (Quickstart, Operators guide).

Schema evolution chalkashligi O'RTA

Producer va Consumer'lar alohida deploy bo'ladi. Schema o'zgarsa, eski consumer break bo'lishi mumkin.

Mitigatsiya: Karapace Schema Registry + BACKWARD compatibility majburiy. Yangi field — har doim optional. Field o'chirish — alohida deploy.

Outbox poll latency O'RTA

Scheduled poller 1 sekund interval — peak load'da Kafka publish kechikishi mumkin (5-10s).

Mitigatsiya: Stage 4'da Debezium CDC — to'g'ridan-to'g'ri DB WAL → Kafka (sub-second latency). Yoki Postgres LISTEN/NOTIFY trigger.

Disk to'lib qolish PAST

Retention 30 kun, peak ~50 event/sec → ~130GB/oy. SSD 500GB — 3 oy chidaydi.

Mitigatsiya: Tiered storage (Stage 4) — eski event'lar S3/MinIO'ga. Prometheus alert — disk >70%.
